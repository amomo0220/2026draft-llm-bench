# COUNCIL.md：予想会議（マルチエージェント）の追加実験

`docs/PLAN.md` のベンチマーク本体とは **別の追加実験** として扱う。本体と共通にするのは仕組み（スキーマ・採点・候補者マスタ・実行ログの形式）だけで、問いと結論は分ける。

- 本体の問い: 情報条件・ハーネスで予測がどう変わり、どこでハルシネーションが起き、ベースラインにどれだけ勝てるか
- この実験の問い: **同じモデル・同じ情報・同じトークン予算のとき、役割を分けて合議させると、1エージェントで何度も答えさせて集約するより予測が良くなるか**

本体の結果表に M / S を混ぜない。記事でも、本体（note 前後編の主役）と別の枠（後編のおまけ・Zenn 技術記事）で扱う。

## 2. 条件

| 条件 | 内容 |
| --- | --- |
| M 予想会議 | 3役が独立に予測 → 互いの案を読んで修正 → 議長が最終予測を出す |
| M-avg 機械的集約 | M の Round 1 の3案を機械的に平均する。LLM は呼ばない。議長の付加価値を測るために使う |
| S 同予算シングル | M と同じトークン量を、1エージェントが独立に k 回予測して集約するのに使う |

共通の設定:

- **モデル**: 全役割・全条件で **`claude-sonnet-5-5`** の1モデルだけを使う（2026-10-15 決定）。合議という仕組みの効果だけを見るため、またコストを抑えるため。ロッテのサブロー監督が今年 Claude を使うと報じられていることから（企画の題材とそろえる）、Anthropic のモデルにした。モデルIDはログに残す
- **情報**: 本体の **条件B（候補者マスタのみ）** と同じ。10/21 時点の `data/candidates.csv` のスナップショットを全役で共有する。Web検索・MCP は使わない
- **タスク**: 本体と同じ予測（12球団の1位入札・競合・ロッテ1〜5位）。出力は `PredictionOutput` で検証する。提言ではなく予測であることをプロンプトで明示する
- **実行回数**: M・S それぞれ3回

## 3. 条件M：予想会議

### 3.1 役割（中立の立場）

特定の球団の編成会議にはしない。「この球団は誰を獲るべきか」という視点が「誰を入札するか」の予測に混ざるのを防ぐため、全員を **ドラフトを外から予想する中立の立場** にする。

| 役割 | 見る観点 | 方針 |
| --- | --- | --- |
| 球団動向担当 | 各球団の補強ポイント、過去の指名傾向、編成方針 | 球団側の事情から、どの球団が誰に入札するかを読む |
| 選手評価担当 | 各球団のスカウトがどの選手を上位に評価しそうか | 選手側から、人気が集中する選手・競合を読む |
| 検証担当 | 候補者マスタとの照合 | 下の3.2のとおり。事実で確認できない主張に反論する |
| 議長 | 中立 | 自分の候補は出さず、議論を集約して最終予測を出す |

- プロンプトは `prompts/council/` に置く。役割は `teams.md`・`players.md`・`verifier.md`・`chair.md`、会議の共通ルールは `common.md`、発言の種類は `round0.md`・`round1.md`・`final.md`
- system は 本体の `prompts/system.md`＋`common.md`＋役割、user は 本体の `context_B.md`（候補者一覧）＋発言の種類＋本体の `task.md`（スキーマだけ会議用）
- 3役とも、本体と同じく自分の `PredictionOutput` を出す（M-avg で3案を平均するため）。出力は `{"argument": 発言, "prediction": PredictionOutput}`（`src/council.py` の `CouncilTurn`）

### 3.2 検証担当の役割

条件B のコンテキストは候補者マスタ（区分・氏名・所属・ポジション）だけで、成績や指標は入っていない。そのため「数字で裏付ける」役を置くと、モデルが学習データから成績を作ってしまい、ハルシネーションを増やす。検証担当は数字を出させず、**マスタで確認できる事実だけ** を扱う。

- 他の役の案に出た選手が、候補者マスタにいるか（いなければ、プロ志望届を出していない可能性を指摘する）
- 氏名・所属・区分（高校・大学・社会人など）がマスタと合っているか
- 同じ選手が複数の球団の1位入札で最有力になっているのに、競合予測に入っていない、などの矛盾
- 検証担当自身の予測は、マスタで確認できる選手だけを使った保守的な案にする

これにより、本体のハルシネーション指標（マスタにない名前の割合など）で、合議によって名前の誤りが減るかも見られる。

### 3.3 進行

1. **Round 0（独立提案）**: 3役がそれぞれ、他の役の発言を見ずに `PredictionOutput` と根拠を出す
2. **Round 1（反論と修正）**: 決められた順番で発言する。各役は他2役の Round 0 案と、自分より前に発言した役の Round 1 発言を読み、反論を書いたうえで修正版の `PredictionOutput` を出す
3. **Final（集約）**: 議長が Round 1 の3案と議論を読み、最終の `PredictionOutput` を出す

Round 1 の発言順は、run ごとに変える（最初の発言者に引きずられていないかを見るため）。

| run | Round 1 の発言順 |
| --- | --- |
| 1 | 球団動向 → 選手評価 → 検証 |
| 2 | 選手評価 → 検証 → 球団動向 |
| 3 | 検証 → 球団動向 → 選手評価 |

### 3.4 M-avg（機械的集約）

Round 1 の3案から、次のルールで決定的に作る（S の集約と同じ関数を使う）。

- 1位入札: 球団ごとに、選手ごとの確率を3案で平均する
- 競合予測: 平均後の1位入札から、最有力候補が重なる球団を数えて作り直す
- ロッテ1〜5位: 順位ごとの多数決。同数なら、その選手のロッテ1位入札の平均確率が高い方、それも同じなら案の並び順で先の方

## 4. 条件S：同予算シングル

- M と同じモデル・同じ情報・本体と同じプロンプト（条件B）で、独立に `PredictionOutput` を k 回生成する
- **予算をそろえる**: 同じ番号の M の run の総トークン数（入力＋出力）を測り、S の累計がその ±10% 以内に入るまで生成を続ける。k は自動で決まる
- 集約は 3.4 と同じルール
- 実際の k と総トークン数をログに残す

## 5. 未成年の選手への配慮

議論の形式では、他の役の推す選手を否定する発言が出やすい。候補には高校生（未成年）が含まれるため、プロンプトの段階で次を制約する。

- 議論は **指名の予測の根拠**（球団の事情・指名傾向・マスタとの照合）で行い、選手個人の短所や欠点を述べない
- 反論の対象は「他の役の予測」であって「選手」ではない

公開時のルール:

- 議事録の全文はリポジトリに置いてよい。note・Zenn に引用するのはハイライトだけにし、引用の前にリポジトリのオーナーが確認する
- 選手個人を貶める表現は引用しない

## 6. 保存先とログ

本体の形式（`predictions/{condition}/{model_id}/{run_id}.json`、`runs/runs.jsonl`）に合わせる。保存先のディレクトリは `--predictions` で必ず指定する（既定値はない）。

```
predictions/2026-10-21/                          # 保存先の例（2回目の事前登録の扱いは 8章）
├─ M/claude-sonnet-5-5/{run_id}.json             # 議長の最終予測（採点対象）
├─ M-avg/claude-sonnet-5-5/{run_id}.json         # 機械的集約（採点対象）
└─ S/claude-sonnet-5-5/{run_id}.json             # 同予算シングルの集約（採点対象）
runs/council.jsonl                               # 1行＝1回の LLM 呼び出し（途中の案はここだけ）
runs/runs.jsonl                                  # M・M-avg・S の1回ごとの合計（本体と同じ形式）
```

- **途中の案（Round 0・Round 1・S の各回の予測）は `predictions/` に置かない。** 採点スクリプトは `predictions/` の下の JSON をすべて読むので、置くと途中の案まで採点されてしまう。途中の案は `runs/council.jsonl` の `prediction_json` に残す
- `runs/council.jsonl` の項目: `run_id, condition, run_no, round, role, speaker_index, model_id, prompt_sha256, input_tokens, output_tokens, cost_usd, latency_ms, attempts, api_retries, status, error, content, prediction_json, timestamp, target_tokens, k`
  - `round` は `round0` / `round1` / `final`（M）、`sample` / `summary`（S）
  - `content` は発言（argument）。スキーマに違反した出力は、その本文を残す
  - S の `summary` 行に、そろえる先のトークン数（`target_tokens`）、有効な予測の数（`k`）、実際に使ったトークン数を残す。±10% に入らなかったときは `status=budget_mismatch`

## 7. 評価

### 7.1 主な指標（結論に使う）

本体と同じ採点（1位入札的中率、ブライアースコア、ロッテ1〜5位の一致、マスタにない名前の割合）を M / M-avg / S に適用し、次の3つだけを比べる。

| 比較 | 見ること |
| --- | --- |
| M vs S | 合議は、同じ予算の1エージェントより良いか |
| M vs M-avg | 議長は、単純平均より良いか |
| コスト | M・S それぞれの総トークン数・金額・時間 |

### 7.2 観察（結論には使わない）

1回のドラフト、1位は12枠、各3run という規模では、次の値に統計的な差は出せない。記事では「観察」と明記し、付録として扱う。

| 観察 | 定義 |
| --- | --- |
| 意見変化率 | Round 0 → Round 1 で、各役の1位入札の最有力候補が変わった割合 |
| 変化の当否 | 変わったもののうち、正解に近づいた割合と遠ざかった割合（採点後） |
| 先手追従率 | 議長の最終予測が、Round 1 で最初に発言した役の案と一致した割合 |
| 発言順感度 | 発言順の違う3run で、12球団の1位の最有力候補がどれだけ一致したか |
| 候補の多様性 | Round 0 に出た候補選手のユニーク数（M の3役の合計 vs S の k 回の合計） |
| 名前の訂正 | 検証担当の指摘で、マスタにない名前が最終予測から消えた件数 |

集約と指標の計算コードには、ダミーの正解データでのユニットテストを先に作る。

計算は `uv run python -m src.council_metrics`（正解が出たら `--actual data/actual/2026.json` を付けると変化の当否も出る）。結果は `results/council_observations.json`。先手追従率は、最初の発言者との一致（`first_speaker_agreement`）と、他の2人との一致の平均（`other_speakers_agreement`）を並べて見る。

## 11. 実装と使い方

| ファイル | 役割 |
| --- | --- |
| `src/council.py` | M（会議）・M-avg・S の実行、ログ、見積もり |
| `src/aggregate.py` | 機械的集約（M-avg と S で共通。3.4） |
| `src/council_metrics.py` | 7.2 の観察の計算 |
| `prompts/council/` | 会議のプロンプト |
| `tests/test_council.py`・`test_aggregate.py`・`test_council_metrics.py` | 偽の API とダミーデータでのテスト |

```bash
uv run python -m src.council --predictions predictions/2026-10-21 --dry-run              # 見積もりだけ
uv run python -m src.council --predictions predictions/2026-10-21 --run-nos 1            # run 1 だけ（試し）
uv run python -m src.council --predictions predictions/2026-10-21                        # run 1〜3
uv run python -m src.council_metrics                                                     # 観察の計算
```

- モデルの既定値は `claude-sonnet-5-5`（2章）。run 番号で Round 1 の発言順が決まる（3.3）
- 1つの run 番号で M → M-avg → S の順に実行する。S の予算は、直前の M の実際のトークン数で決まる。M が失敗した run は、M-avg と S も作らない
- 予算の確認は本体と同じく **見積もりの上限** で行う。上限は「すべての発言が出力の上限（32,000 トークン）を使い切り、すべて出し直しになる」場合で、3run で約 $80 になる。目安（発言1つ 6,000 トークン、出し直しなし）は約 $5。`BUDGET_USD` は上限に合わせて設定する（試しの1run は約 $27）
