# PLAN: プロ野球ドラフト × AIエージェント ライブ予測ベンチマーク

最終更新: 2026-10-14

## 1. 概要

2026年プロ野球ドラフト会議（**2026-10-22**）の指名結果を、LLM／AIエージェントに事前予測させ、
ドラフト後に自動採点する。予測はドラフト前に GitHub のタグで固定する（事前登録）。

ドラフトは「モデルの学習データに答えが含まれない未来の出来事」で、「決まった日に答え合わせができる」。
データ汚染のないライブ予測ベンチマークとして使える題材である。

### 問い

- 検索・コンテキスト・ハーネスの違いで、予測はどう変わるか
- どこで・どのくらいハルシネーションが起きるか
- 単純なベースライン（メディア予想の多数決など）にどれだけ勝てるか
- コスト・時間・精度のトレードオフはどうなるか

「どのAIが賢いか」のランキングは主目的にしない。

### きっかけ

千葉ロッテマリーンズのサブロー監督が、ドラフト・外国人選手の情報収集に Claude Code を使うと報じられた
（昨年は ChatGPT に相談していたと話題になった）。ネット上では「Claude Code はモデルではなくハーネス」
という反応もあり、**モデルとハーネスを切り分ける** ことが本企画の技術的な論点になる。

## 2. 設計方針

従来の「ChatGPT vs Claude vs Gemini」型の比較には次の問題があるため、以下の方針で回避する。

| 問題 | 方針 |
| --- | --- |
| モデル・検索・ハーネス・与える情報が同時に違い、差の原因が分からない | 条件を分けて比較する（3章） |
| 「良い指名」には正解がない | 採点できる **予測**（実際に誰が指名されるか）を主対象にし、戦略の **提言** は主観評価として分ける |
| 1回の実行ではノイズと区別できない | 各条件を最低3回実行し、ばらつきも報告する |
| 比較対象がないと付加価値を言えない | ベースラインを2つ用意する |

## 3. 実験設計

### 3.1 予測タスク

1. **12球団の1位入札**：各球団が入札する選手（確率付き）
2. **競合予測**：競合する選手と、競合する球団数
3. **千葉ロッテマリーンズの1〜5位指名**（1位は「入札する選手」。抽選の結果や外れ1位は採点対象外で、`data/actual/` に別途記録する）
4. （提言・参考）ロッテが「指名すべき」1〜5位とその理由 ※採点対象外、主観評価

### 3.2 情報条件

| 条件 | 内容 | 見たいこと |
| --- | --- | --- |
| A 情報なし | 学習データのみで回答 | ハルシネーションの発生状況 |
| B 固定コーパス | 候補者マスタ（`data/candidates.csv` の区分・氏名・所属・ポジション）をコンテキストに入れる | 情報をそろえたときの判断力 |
| C Web検索 | 各社APIのネイティブ検索を使う（候補者マスタは渡さない） | 最新情報の収集力 |
| D エージェント | draft-db MCP＋検索＋自己検証 | 自律的な収集・検証の効果 |
| H ハーネス比較 | Claude Code / Codex / Gemini CLI に同じ draft-db MCP を渡す | モデルとハーネスの切り分け |

モデルは OpenAI・Anthropic・Google の各1モデル。**2026-10-14 に固定**: 各社の最新の中位モデルで格をそろえる（料金も近い帯）。

| 提供元 | モデルID | 料金（入力/出力、100万トークンあたり） |
| --- | --- | --- |
| Anthropic | `claude-sonnet-5-5` | $2 / $10 |
| OpenAI | `gpt-5.6-terra` | $2 / $12 |
| Google | `gemini-3.8-flash` | $0.75 / $3.75（2026年末までの導入価格） |

- 知識のカットオフ（2026-10-15 確認）: Claude Sonnet 5.5 は 2026年6月（Anthropic の公式ドキュメント）、Gemini 3.8 Flash は 2026年3月（Google DeepMind のモデルカード。検索結果で確認し、ページはこの環境から開けなかった）、GPT-5.6 Terra は 2026-02-16（Box・OpenRouter などの二次情報。OpenAI の公式では未確認）。条件 B の予想は、名簿と各モデルのカットオフまでの知識で決まるため、条件 B のモデル間の差には知識の新しさの差が含まれる
- 選定理由: 記事の読者が検索する最新モデル名にする／1社だけ上位モデルにすると比較が不公平に見える／ハーネス比較（H）でも同じ `claude-sonnet-5-5` を使える
- 推論（thinking・reasoning）の設定は各社の既定のまま。出力は各社の JSON モードで受け取り、`PredictionOutput` で検証する。スキーマ違反は1回だけ出し直しを求める
- プロンプトの「今日は○年○月○日です」は、実行時に日本時間の日付で埋める（`{{TODAY}}`、2026-10-14 決定）。日付が変わるとプロンプトのハッシュも変わる
- 本番は、モデル × 条件ごとに1回ずつ3回に分けて実行する（2026-10-14 決定）。1回ごとに見積もりと予算を確かめられ、途中で失敗しても他の回に影響しない。`BUDGET_USD` は 25
  - 例: `for i in 1 2 3; do uv run python -m src.run --condition D --model claude-sonnet-5-5 --n 1 --start $i; done`
- 本番の実行は、織田翔希選手（横浜高）の進路表明（2026-10-15 予定）の後にする。21:00 の公開に間に合うよう、遅くとも 18:00 には始める（3.7）
- 実行は `src/run.py`（現在は条件 A〜D）。モデルと料金の定義は `src/models.py`
- 条件 B は **候補者マスタのみ**（2026-10-14 決定）。球団情報（補強ポイントなど）は主観的な二次情報になりやすく、締切までに一次情報で作れないため入れない
- 条件 C は **2段階**（2026-10-14 決定）: ① 調査（Web 検索あり、自由文の調査メモ。各事実に情報源 URL を付ける）→ ② 整形（検索なし、調査メモと出力形式の指示から JSON を出力）。同じプロンプトで JSON の出力まで1回で求めると Gemini が検索しなかったため（下の試行結果）、3社とも同じ2段階にそろえる。調査メモは予測と同じ場所に `<run_id>.research.md` として保存し、出典の裏付けの確認に使う
- 条件 D は **3段階のエージェント**（2026-10-14 決定）
  1. 調査: Web 検索（条件 C と同じ各社のネイティブ検索）＋ draft-db のツールを使い、自由文の調査メモを書く。候補者マスタは最初から渡さず、必要に応じてツールで引かせる
  2. 整形: ツールなし。調査メモから JSON を出力する（条件 C の2段目と同じ）
  3. 自己検証: draft-db のツールだけを使い、整形した JSON の全選手（氏名・所属・ポジション）をマスタと照らし合わせ、誤りを直した JSON を出力する。どこを直すかはモデルが判断し、コードは突合結果を渡さない
  - スキーマ違反の出し直しは、自己検証の出力に対して1回だけ（ツールなし）。調査メモと自己検証前の JSON も `<run_id>.research.md` / `<run_id>.draft.json` として保存する
  - draft-db のツール: `search_players`（氏名・ふりがな・所属の部分一致。異体字・空白は採点と同じ正規化）と `get_player`（`player_id` で1人の全項目）。`get_team_needs` は外した（条件 B と同じく、球団情報は一次情報で作れないため。球団の事情は Web 検索で調べさせる）
  - API の実行では、MCP サーバーと同じ関数（`src/draft_db_mcp/tools.py`）を各社の関数呼び出し（function calling）として渡す。通信方式が違うだけで、ツールの名前・説明・引数・中身は MCP サーバー（条件 H 用）と同じ
  - 1つの段階でのツール呼び出しの往復は最大20回。Gemini は Google 検索と関数呼び出しの併用に `tool_config.include_server_side_tool_invocations` が必要
- 条件 C の検索: Anthropic は `web_search_20260209`（1回の呼び出しで最大10回）、OpenAI は `web_search`（最大10回）、Gemini は Google 検索のグラウンディング（回数の上限は設定できない）。整形の呼び出しは検索なしなので、条件 A・B と同じく各社の JSON モードを使う。スキーマ違反の出し直しは整形だけをやり直す
- 検索の料金（1回あたり）は `src/models.py`。2026-10-14 に Anthropic（$0.01）と Google（$0.014、検索語1つあたり）を公式の料金ページで確認した。OpenAI の検索（$0.01）は、ユーザーが保存した公式ページの HTML で確認した。gpt-5.6-terra のトークン単価（$2 / $12、Standard・短いコンテキスト）は、ユーザーが公式のモデル仕様と料金表で確認した（2026-10-14）。入力が 272,000 トークンを超えるリクエストはリクエスト全体が $4 / $18 になる。条件 D の試行（入力は全リクエストの合計で約46万）では1回あたりはこれより小さいとみて、コストは通常の単価で計算し、超えたリクエストがあれば実行時に警告する（`runs.jsonl` の `max_request_input_tokens`）。長いコンテキストの割増は、Anthropic（Sonnet 5.5）には **ない**（1M トークンまで通常の単価。公式の料金ページで確認）。Gemini 3.8 Flash の 200K 超の単価は公式で確認できていない（試行では入力が全リクエストの合計でも約10万で、影響しない）Gemini の検索は月5,000件まで無料だが、記録するコストは無料枠を考えない定価で計算する
- Anthropic の API キーは `BENCH_ANTHROPIC_API_KEY` から読む（クラウド環境では `ANTHROPIC_API_KEY` が Claude Code 自身の認証用に予約されているため）

#### 本番の結果（2026-10-15、1週間前予想。`predictions/`・`runs/runs.jsonl`・`results/prereg_report.md`）

条件B〜D × 3モデル × 3回の27回すべてで予測がそろった（実行は30回。Claude 条件D の失敗3回を含む）。記録されたコストの合計は $18.14。

- **Claude 条件D 1回目の失敗**: 調査メモが空のまま終わった（`stop_reason=tool_use(last=thinking)`）。関数呼び出しなしの tool_use で、最後のブロックが思考のまま止まったとみて、サーバー側ツールの途中停止と同じく送り返して再開するよう直した（`src/runners/anthropic_api.py`）。1回のリクエストの入力は最大68万トークンで、生の応答は残っていないため、原因は確定していない。想定外の停止では往復と再開の回数も記録するようにした
- **クレジット不足**: Claude 条件D の1回目の再実行と3回目が、Anthropic のクレジット残高不足（400）で止まった。ユーザーがクレジットを追加した後、同じ番号で再実行して成功した。止まった2回は、止まるまでに使ったトークンが記録されていない（ランナーが例外で中断するとそれまでの使用量を返さないため）。実際の請求は記録より多い → 後日直す
- **Gemini 条件C 1回目は検索0回**だった（2回目は8回、3回目は6回）。検索の根拠情報（grounding）がなく、出典はニュースサイトのトップページの URL だけだった。それでも、調査メモには当日（10/15）の織田翔希選手の「高卒でメジャー挑戦」の表明が書かれていた（表明の内容自体は合っていた）。一方で、志望届の提出日など誤った記述もあった。検索の記録が返らなかっただけなのか、知識からの推測なのかは区別できない。ユーザーと相談し、やり直さずに記録として残し、調査メモも公開する（2026-10-15 決定）
- **スキーマ違反**: 27回とも出し直しなしで通った（条件D の `attempts=2` は、整形と自己検証の2段階でそれぞれ1回ずつ JSON を出力した数）
- **名簿にない名前**: 27回のうち、Gemini 条件C の2回で同じ1人（社会人の外野手）だけ。3.4 の手順で後日確認する
- **長いコンテキスト**: OpenAI の1回のリクエストの入力は 272K を超えなかった（割増なし）
- 実行中に見つけた不具合: 予測の読み込み（`src/scorer.py`）が条件 D の自己検証前の下書き（`*.draft.json`）まで読んでいたので直した

基本は **3モデル × 条件A〜D × 各3回 ＝ 36回** ＋ ハーネス比較。

### 3.3 ベースライン

- **メディア予想の多数決**：スポーツ紙・専門誌の「12球団1位予想」を集計したもの（集計値のみ保存）
- **評価順ルール**：評価の高い順に、空いている選手を指名するだけの単純ルール

#### メディア予想の集め方（2026-10-14 決定）

- 集める日: **10/16〜17**。AI の予想（10/15）に近い時点の予想と比べないと不公平になるため。前日（10/21）の予想は各球団の1位公言を反映しているので、集めるとしても参考扱いにする
- ドラフトの前に集めてコミットする（後から集めると、当たった媒体を選ぶ偏りが入る）
- 対象: スポーツ紙・専門誌・Web 媒体の「12球団の1位予想」の記事。媒体ごとに、記事の公開日と URL を記録する
- 保存するのは構造化したデータだけ（記事の本文は保存しない。AGENTS.md ルール4）
  - `data/baselines/media_picks.csv`: `outlet, published_on, source_url, team, player_name, affiliation, position`（1行＝1媒体の1球団）
  - 多数決: 球団ごとに、媒体の数で割った割合を確率とみなす。採点は1位入札の指標（的中・ブライアースコア・ポジション）だけ。ロッテの2〜5位を予想する媒体は少ないので対象外
- 有料記事や、表が画像だけの記事は読めないことがある。集めた結果はユーザーが目で確かめる
- 実装（未着手）: `src/baselines.py` で CSV を検証・集計し、採点に渡す

### 3.4 候補者マスタ（正解判定の基準）

- プロ志望届の提出者一覧（高校・大学）＋ 社会人・独立リーグの主な候補 → `data/candidates.csv`
- 高校生・大学生は志望届の提出が指名の前提。**志望届を出していない高校生・大学生の名前が出たら、ハルシネーション（または指名不可）と判定**できる
- 列: `player_id, name, kana, category(高校/大学/社会人/独立/二軍参加), team, position, throws_bats, source_url`（検証は `src/candidates.py`）
- `player_id` は区分ごとの接頭辞＋3桁の連番: `HS-001`（高校）／`UN-001`（大学）／`SH-001`（社会人）／`IN-001`（独立）／`FM-001`（二軍参加＝オイシックス・ハヤテ）
- 社会人・独立・二軍参加には志望届がなく、一次情報の候補者一覧が存在しないため網羅しない。「競合候補」などの記事に出てくる主な候補だけを `data/candidates_extra.csv` に手で追加する
- 高校・大学は、公式の志望届一覧ページを `data/raw/` に保存し、`uv run python -m src.build_candidates` で生成する（「NPBドラフト対象者」の表のみ。ページの合計人数と一致しなければエラー。再生成しても既存の `player_id` は変わらない）
- 現在の出典: 高校＝日本高等学校野球連盟（2026-10-08 17時時点、127名）、大学＝全日本大学野球連盟（149名、ふりがな付き）
- 公式一覧でも表示できない異体字（「𠮷」「髙」「﨑」など）がある。採点時の名前の突合では異体字をそろえる
- 社会人・独立・二軍参加の出典（二次情報）: 「ドラフト1位競合候補6人」（ベースボールチャンネル、2026-10-04）、週刊ベースボール 2026年5/11・18号の目次（2026-04-28）、「社会人・独立リーグ ドラフト候補選手名鑑2026」（ベースボールチャンネル、2026-09-01）。計14人

#### マスタにない名前の判定（社会人・独立は網羅できないため）

- 予測に出た名前のうち、マスタと突合できなかったものは、すぐにハルシネーションとはせず **要確認** とする
- 全条件の予測がそろった後、要確認の名前だけを一次情報（チーム・リーグ公式の選手名簿など）で確認し、次の3つに分類する
  1. **実在・指名可能**（社会人・独立・二軍参加の選手）→ 出典URLと確認日を付けて `candidates_extra.csv` に追加する
  2. **実在・指名不可**（志望届を出していない高校生・大学生、NPB所属選手など）→ 指名不可として扱う
  3. **実在を確認できない** → ハルシネーション
- 予測ファイルは変更しない。確認結果とマスタへの追記はコミット履歴に残す（事前登録後でも、採点側のデータとして追記してよい）

### 3.5 出力スキーマ（初期案）

```python
class FirstRoundBid(BaseModel):
    team: TeamCode                      # 12球団コード
    candidates: list[PlayerProb]        # 入札候補と確率（合計 1.0）

class PlayerRef(BaseModel):            # 予測に出てくる選手（共通部分）
    player_name: str
    affiliation: str                    # 所属（高校・大学・企業・独立球団など）
    position: Position                  # 投手 / 捕手 / 内野手 / 外野手（NPB のドラフト結果と同じ4区分）

class PlayerProb(PlayerRef):
    prob: float

class LottePick(PlayerRef):
    round: int                          # 1〜5（1位 = 入札する選手）
    reason: str
    sources: list[HttpUrl]

class PredictionOutput(BaseModel):     # LLM が出力する部分（LLM にはこれだけを渡す）
    first_round: list[FirstRoundBid]    # 12件
    contested: list[ContestPrediction]  # 競合予測（最小構成では空でよい）
    lotte: list[LottePick]              # 5件

class Prediction(BaseModel):           # predictions/ に保存する単位
    run_id: str                         # 以下3つはコードが付与する
    model_id: str
    condition: str                      # A / B / C / D / H-claude / ...
    output: PredictionOutput
```

実装は `src/schema.py`。メタデータ（run_id・model_id・condition）は LLM に書かせず、実行スクリプトが付与する。

LLM には **選手名・所属・ポジション** を出力させる（`player_id` は出力させない）。候補者マスタとの突合は採点側のコードで名前によって行い、結果は予測ファイルに書き戻さない。突合できない名前は「要確認」として扱う（3.4）。所属とポジションは、誤りの判定と、要確認の名前の確認に使う。これにより、事前登録後でも突合ロジック（表記ゆれの吸収など）を修正できる。

### 3.6 評価指標

| 指標 | 内容 |
| --- | --- |
| 1位入札的中率 | 最尤候補が実際の入札と一致した球団数 / 12 |
| ブライアースコア | 1位入札の確率予測の校正（確信度の当たり具合） |
| 競合予測精度 | 競合選手の一致、競合球団数の誤差 |
| 指名順の順位相関 | 予測した指名順と実際の指名順のスピアマン相関 |
| 上位k人の的中 | 予測上位k人のうち実際に指名された人数 |
| ハルシネーション率 | マスタにない選手（3.4 の分類で「実在を確認できない」もの）、所属・ポジションの誤り |
| ポジションの的中 | 1位入札（各球団の最尤候補）とロッテ各順位について、予測したポジションが実際の指名選手のポジションと一致したか。選手を外しても「投手を取る」という読みが合っていたかを測る |
| 出典の裏付け率 | 出典URLが主張を裏付けているか（LLM-as-a-Judge＋人手の抜き取り確認） |
| コスト・時間 | 金額、トークン数、所要時間、ツール呼び出し回数 |
| 安定性 | 3回の実行間の一致度 |
| 丸写し度 | メディア予想の多数決との一致度 |

#### 採点の実装（`src/scorer.py`）

- 実装済み: 1位入札的中率、ブライアースコア、ポジションの的中、ロッテ各順位の的中、上位k人の的中（ロッテ5人）、ハルシネーション（3.4 の分類）、所属・ポジションの誤り
- 未実装: 競合予測精度、指名順の順位相関、出典の裏付け率、安定性、丸写し度、コスト・時間（実行ログから集計する）
- ブライアースコア: 球団ごとに候補の確率を合計1に正規化し、候補にない選手が入札された場合は「その他（確率0）」が正解とみなす多クラス版。0が最良、2が最悪
- ロッテ: 1位は予測と実際の **入札** を比べる。2〜5位は実際に支配下で指名があった順位だけを採点する。上位k人の的中は、実際に獲得した選手（1位は最終的な1位）と比べる
- 名前の突合: NFKC 正規化、異体字の統一（𠮷→吉、髙→高、﨑→崎、澤→沢 など）、空白・中黒の除去。同姓同名は所属で絞る
- 入力
  - `data/actual/2026.json`: ドラフト当日に人手で入力する（`uv run python -m src.actual` で検証）。各球団の1回目の入札・抽選の勝敗・最終的な1位と、ロッテの2〜5位（支配下のみ）。ポジションは NPB 公式の4区分
  - `data/name_checks.csv`: マスタにない名前の確認結果（`name, verdict, checked_on, source_url, note`。verdict は `ineligible`＝指名不可、`not_found`＝実在を確認できない）。実在・指名可能だった選手はここではなく `candidates_extra.csv` に追加する
- 出力: `results/run_scores.jsonl`（1実行1行）、`results/summary.csv`（モデル × 条件ごとの平均と標準偏差）、`results/pending_names.csv`（未確認の名前。出現した実行数の多い順）
